# 个人工作说明：从需求讨论到设计规格

> 项目：IdeaFlow 多 Agent 人机协同需求分析与设计规格工作台  
> 分支：`FYC`  
> 范围：`modules/requirements`、需求侧 Web 工作台、`eval`、相关文档  
> 边界：不修改 `modules/orchestrator` 的执行逻辑，不擅自修改 `contracts/v2` 既有字段

## 1. 项目定位

IdeaFlow 解决的是“一句模糊需求无法直接进入开发”的问题。系统把一句想法拆成两条链路：

```text
讨论链路
一句话
  → 澄清
  → 六角色独立发散
  → 多轮结构化批判/回应
  → 整合与候选方案
  → 立场签署
  → 复核与收敛
  → proposal.md + blackboard.json + events.jsonl

规格链路
一句话 / 案例
  → 需求快照（R/C/Q）
  → 可选：讨论增强 + 功能归纳
  → A/B 两份独立草案
  → 逐份评审与整合
  → 设计规格 spec.json / spec.md
  → 自审查
  → 自动修订或人工升级
  → 任务计划 plan.json
```

本人主要负责需求侧：讨论引擎、真实模型接入、讨论到规格的桥接、功能归纳、规格数据质量、
需求侧 Web 工作台与评测工具。

## 3. 详细工作

### 3.1 六角色讨论引擎

讨论按七阶段推进：

1. 首轮澄清：需求分析角色提出只能由人回答的阻断问题；
2. 独立发散：六个角色并行生成主张，上下文互不可见；
3. 结构化批判：必须引用论点编号，给出严重度与后果；
4. 回应：被点到的角色逐条回应，立场为接受/反驳/有条件；
5. 整合：记录员去重聚类，保留来源与少数意见，生成候选方案；
6. 立场签署：六角色对候选方案表态；
7. 收敛：判断共识、待验证或价值冲突。

六个讨论角色：

| ID | 角色 | 关注点 |
| --- | --- | --- |
| `ba` | 需求分析 | 用户、场景、问题、功能需求与信息缺口 |
| `user` | 用户视角 | 画像、使用场景、痛点真实性与迁移成本 |
| `tech` | 技术专家 | 可行性、依赖、实现难点与技术风险 |
| `innovation` | 创新顾问 | 替代方案、差异化与更小切口 |
| `risk` | 风险评估 | 成本、进度、安全、数据与实施风险 |
| `skeptic` | 质疑者 | 挑战关键假设、寻找逻辑跳跃与反例 |

`记录员/整合者` 与 `主持人` 由代码调度，不参与并行发散。

讨论结果不是“投票平均”，而是显式记录：

- 阻断异议是否被回应；
- 事实缺口转待调研；
- 价值取舍交人工；
- 少数意见进入 Proposal 第 11 章，不删除；
- 连续两轮无新增问题可提前终止。

### 3.2 真实模型接入

实现 OpenAI 兼容 `LLMAgent`：

- `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL` 配置，支持 DashScope、千问 MaaS、DeepSeek；
- 每个阶段独立提示词、温度与输出形状；
- 模型输出先做契约校验，失败时把错误与目标形状回注，最多重试两次；
- 单角色失败只跳过该角色并写 `warnings`，不中止整条运行；
- 调用记录写 `ai_calls.jsonl`：阶段、角色、耗时、token、状态、错误。

兼容性开关：

| 变量 | 用途 |
| --- | --- |
| `AI_JSON_MODE=0` | 关闭 `response_format`，适配不支持的模型 |
| `AI_EXTRA_BODY` | 透传 `enable_thinking=false` 等厂商参数 |
| `AI_TIMEOUT` | 单次调用超时 |

真实模型常见问题与处理：

| 现象 | 处理 |
| --- | --- |
| `claims` 是字符串数组 | 澄清阶段丢弃非对象项 |
| 异议/回应引用不存在编号 | 过滤未知编号；为空则回注重试 |
| 跨角色复核自己的论点 | 复核前按 `own claims` 过滤 |
| 空 `responses` / `reviews` | 视为可重试错误，回注“至少一条” |
| 字段是数组/数字而非文本 | 统一转字符串并补默认值 |
| 草案 `cost_days="2 天"` | 提取数字；`satisfies` 中文映射枚举 |
| 整合缺 `narrative`/工作包 | 补默认叙事与合法三点估算 |
| 功能来源 `CLM-xx` 无 R 编号 | 保留 `F-xx` 并进待确认，不伪造需求 |

### 3.3 讨论接入规格

`specflow.run(..., discuss=True)` 的顺序：

1. 先跑讨论，产物写 `target/discussion/`；
2. 用黑板增强快照；
3. 生成功能清单；
4. 进入 A/B 草案、评审、规格、审查。

快照映射规则：

| 讨论结论 | 快照条目 |
| --- | --- |
| 假设 | `open`，前缀“推断假设：” |
| 未解决待澄清 | `open`，阻断项 `must` |
| 未解决阻断异议 | `open`，`priority=must` |
| 非目标 | `constraint`，“不做 X” |
| 方案范围 | `requirement`，“范围：…” |

默认 `discuss=False`，旧离线入口不退化。讨论产物的 `ai_calls.jsonl` 合并到规格运行目录，
便于统计整条链路的真实调用次数。

### 3.4 快照治理

讨论四轮后曾出现 161 项快照、原文只有 7 条的情况，评审无法阅读。处理：

- 去空白与中英文标点后归一化去重；
- 假设去掉“推断假设：”前缀后与原文比对；
- 讨论补充上限为原文条数的 2 倍；
- `must`（阻断、非目标）不参与截断；
- 来源增加 `actor`、`round`，可追溯到角色与轮次；
- 契约同步为可选字段，旧产物不受影响。

结果：同一案例从 161 项降到 24 项，阻断项全部保留。

### 3.5 功能归纳

新增 `features` 阶段，Mock 与真实模型都实现：

- 输出 3–12 条功能；
- 名称 2–24 字，写能力，不写“问题定义/关键路径/全部范围/结构边界”；
- 每条 `source_refs` 至少一个真实编号（`CLM/OPT/R`）；
- `inferred` 标明是否为讨论推断；
- 校验失败回注重试，仍失败则报 `LLM_BAD_OUTPUT`。

产物 `features.json` 受 `contracts/v2/features.schema.json` 约束。

功能到规格的映射：

| 规则 | 实现 |
| --- | --- |
| 功能 → 需求 | 按功能名/描述关键词匹配快照需求，可覆盖多条 `R-xx` |
| 匹配不到 | 保留 `F-xx`，进 `open_items`，不拿第一条需求顶替 |
| 模块 | 一个功能一个模块，名称唯一，最多 12 个 |
| 验收 | 每个功能独立判据，检索/录入/审批/通知/统计分别生成 |
| 估时 | 取真实工作包或决策成本；取不到写 `null`，不均摊 |
| 依赖 | 按功能语义补最小依赖，推不出时在 `open_items` 提示串行风险 |

### 3.6 规格生成与数据质量

规格生成包含：

- 决策：每条功能/需求一条，记录选择、理由、满足程度、成本、来源；
- 模块：职责、接口、估算、交付物、验收、依赖；
- 映射：需求与模块双向登记；
- 验收：可度量判据；
- 非目标与未采纳意见：保留理由；
- 估算：PERT 三点，承诺取期望加缓冲。

本轮修复的四类数据质量问题：

| 问题 | 修复 |
| --- | --- |
| 6 个功能全部映射到 `R-01` | 按功能关键词匹配需求；未匹配保留 `F-xx` 并进待确认 |
| 6 条验收被覆盖成同一句 | 修订按 `decision_id` 定位；每条功能独立判据，删除通用尾巴 |
| 估时全部均摊为 2.0/6.0 天 | 取真实工作包或决策成本；取不到写 `null` 并记待确认 |
| `depends_on` 全空导致串行图 | 按功能语义补最小依赖；成功后将计划图变成有并行层的 DAG |

修复后复现结果：

```text
映射需求：R-01 / R-02 / R-06 / R-07
验收：6 条互不相同
估时：2.0 / 2.2 / 1.8 / null / null / 1.8
依赖：T1→T2→T3→T4，T4→T5、T4→T6
分层：[T1] [T2] [T3] [T4] [T5,T6]
```

### 3.7 审查、修订与升级

审查覆盖：

- 需求是否有决策、模块、验收；
- 是否超期限；
- 是否违反禁止项；
- 验收是否可度量；
- 需求与模块映射是否双向一致。

自动修订只处理确定性可修的问题：

- 期限冲突：从低价值模块开始裁剪；
- 无需求映射的功能模块：跳过裁剪，不越界；
- 修订记录包含改前/改后、复核结果、解决与残留问题。

无法自动解决的进入人工问题：

- 价值冲突、需求被降级、禁止项无法消除；
- 问题包含背景、选项、成本、后果、影响范围；
- 背景列出其余阻断，避免“3 条阻断只问 1 条”。

### 3.8 导出与一致性

- `spec.vN.json` 与 `spec.vN.md` 同版本、同内容哈希；
- 导出带 `snapshot_ref`、`review_ref`；
- 空需求映射时导出不越界，显示“未映射需求”；
- 讨论补充来源带角色与轮次，可追溯；
- 导出层附加 `artifacts` 字段目前不在 v2 schema 内，验收时需剔除。

### 3.9 需求侧 Web 工作台

- 任务后台执行，前端轮询阶段日志；
- 提案/规格两种模式；
- 真实模型开关：未配置 Key 时返回 `LLM_NOT_CONFIGURED`；
- 角色跳过以黄色警告条显示，含阶段、错误码、消息；
- 错误按类型给提示：配置、调用失败、输出不合格、网络；
- 规格结果展示调用次数、模型、运行目录。

## 7. 已知边界

- `estimate_days: null` 需要测试侧把契约放宽为 `number|null`；
- `/api/start` 直接收一句话仍走编排器 `pm_breakdown`，需要成员4 接规格/计划桥；
- 前端规格页暂未暴露“先跑讨论”开关；
- 依赖规则基于关键词，复杂产品仍需人工补充；
- 讨论轮次默认 2，真实模型 4 轮耗时 1–3 分钟。

## 9. 个人总结

这部分工作解决的核心问题不是“让模型多说话”，而是让多角色讨论的结论能变成可执行、
可追溯、可审查的规格：

- 每个数字有来源：功能追到主张/需求，模块追到功能，规格绑定快照与评审；
- 每个失败可定位：角色、阶段、错误码、字段路径都落盘；
- 每个取舍有记录：未采纳意见、非目标、待确认项不删除；
- 每个结论可验证：离线测试、真实冒烟、A/B 评测三种口径。
